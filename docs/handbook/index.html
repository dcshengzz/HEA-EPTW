HEA Digital Safety Tools (ePTW) — Handbook

A plain-English knowledge base and user manual for the HEA Digital Safety Tools system. The source code calls it "ePTW". It was rebuilt by reading the system's own code and database design, because the original developer left no documentation. It was compiled on 2 October 2026 from the code in the GitHub repository dcshengzz/HEA-EPTW and from the production database design dated 28 September 2026.

Executive summary

HEA Digital Safety Tools is a web system used by Hitachi Elevator Asia (HEA) and its contractors on lift and escalator installation sites in Singapore. It replaces paper safety forms. Each one becomes an online form that is filled in on site, checked by the right people in a fixed order, and kept as a permanent record with photos and GPS location.

What problem does the system solve?
  • Permit to Work (PTW). High-risk work, such as working at height in a lift shaft, may not start until a chain of people has signed off: an assessor, HEA Safety and the HEA Project Manager. The system enforces that order. It keeps the sign-offs, a daily check for each day of the permit, and the final close-out.
  • Toolbox Meeting (TBM). Every shift starts with a short safety briefing. The system records who attended, which hazards were discussed, which lifts or escalators were worked on, an equipment safety checklist, and the supervisor's personal safety declarations. A manager then approves the record. This attendance also produces the "manpower on site" figures.
  • Compliance Check Point (CCP). Some installation steps are critical, for example "Hoisting of Guiderails" or "Setting up of Traction Machine". For each such step on a specific lift, a checklist and photos prove the control measures were in place, and an approver signs it off.
  • Visibility. Each project has a dashboard with charts of all records by status and a 9-day manpower chart. Every permit and toolbox meeting can be downloaded as a PDF.

Five things every manager should know first
  1. There are no notifications. The system never emails anyone when a form needs attention. Approvers must open their Pending list, and applicants must check their own list for returned forms. The only email the system sends is a new or reset password.
  2. Roles decide everything. If someone "can't see the button", the cause is almost always a missing role. Another common cause is that the person does not belong to the project's main contractor. See Roles & Permissions.
  3. Some settings have no screen. Menu items, checklist questions, permit work types and CCP key activities can only be changed by IT directly in the database.
  4. Several known defects exist. Examples: "Lock user" permanently deletes the user, and a permit's closure review never moves it out of the reviewer's list. All of them are listed in Known Issues & Risks.
  5. Errors are often silent. If a button "does nothing", the save probably failed in the background. Typical causes are a remark that is too long or a session that expired. See Troubleshooting.
How this handbook was produced, and its limits

Four reviews were carried out on the system: the database design (33 tables, 124 stored routines), the server-side logic, every screen and form, and the administration screens. The findings were then checked against the code itself. Everything here describes what the code actually does, which sometimes differs from what the on-screen wording promises.

What could not be seen. The database backup contains the structure only, not the data. Three things therefore need to be confirmed on the live system:

  • the exact wording of the left-hand menu items, and which roles see them;
  • the checklist questions inside each template, and the list of PTW work types;
  • the visual layout of the PDF reports.

Wherever this handbook says "menu item (name may differ)", check the wording against the live system. The screen headings quoted in this guide are exact.

Screenshots. Each step has a dashed "Screenshot target" card. It tells whoever captures the screenshot exactly which screen to open, what to highlight, and what sample data to enter.

Getting started: signing in and choosing a project

Every user goes through the same three steps: sign in, pick the project (building site) to work on, then use the menu on the left.

Key terminology
  • User ID. Your email address. HEA staff can type only the part before "@"; the system adds "@hitachi.com" automatically.
  • Project. One building or installation site, for example "Tampines GreenGlade Block 512". Every form belongs to exactly one project.
  • Main contractor. The company named as the project's main contractor. Many approvals and full-visibility rights apply only to staff of this company.
  • Left menu. The work menu (PTW, TBM, CCP, Overview and so on). It appears only after a project is selected.
  • Configuration menu. The right-hand settings panel (users, projects, equipment and so on). You see only what your roles allow.

Permit to Work (PTW)

Core feature

An electronic permit that must be fully approved before high-risk work, typically Work at Height (WAH), may start on a lift unit. The original developer built it to replace the paper permit and its seven signature "Parts". It gives a single, time-stamped record of who allowed the work, who checked it each day, and who confirmed it was finished.

Feature overview: the permit's journey

A permit covers one lift or escalator unit (its Manufacturing Number) for 1 to 7 consecutive days. It passes through four sign-offs before work may begin. During the work it gets a daily check. At the end, the applicant reports completion and the main contractor acknowledges it.

Key terminology
  • Manufacturing Number (MFG No.): the registration number of the lift or escalator unit being worked on. Only equipment registered with the type "MFG NO" appears in the list.
  • Work Type: the kind of risky work, for example Working at Height. Each work type has its own checklist. Work types and their questions are set up by IT.
  • WAH: Work at Height.
  • Total Worker: head-count of workers under this permit (1–1000).
  • Return: send back to the applicant for correction. The permit can be fixed and resubmitted.
  • Reject: refuse permanently. A new permit must be raised.
  • Revoke: cancel a permit that was already approved, usually because of a safety lapse. This is final.
  • Daily Review: a separate tick for each day of the permit, by the applicant and by the assessor.
  • Complete the Permit: the applicant's statement that the work is finished.
  • Closure Review: the main contractor's acknowledgement of completion.

Statuses: SUBMITTED ASSESSED VERIFIED APPROVED CLOSED RETURNED REJECTED REVOKED. The meaning of each is in Glossary & Statuses.

Running example: subcontractor Kong Lift Engineering Pte Ltd needs to install guide rails in lift L2 at "Tampines GreenGlade Block 512" from Thursday 8 to Monday 12 October 2026. HEA is the main contractor.

Highlight

Sample data
Date From 08/10/2026 · Date To 12/10/2026 · Manufacturing Number L-2231 (Lift L2, Passenger 13-person) · Work Description "Installation of guide rails in shaft L2, levels 1–12" · Total Worker 4 · Work Type "Working at Height"

Always start from the menu's New item, so that you get a blank form. Fill in every field. All six are required.

  • Dates: the start date cannot be in the past, and the permit can last at most 7 calendar days. A longer job needs a new permit after this one ends, because renewal is not automatic.
  • Work Type: choosing it reloads the page and shows that work type's safety checklist. Choose the work type first. Changing it later wipes any checklist answers already entered.
In the background: nothing is saved yet. The draft lives only in your browser session until you click Submit. If you close the browser or your session expires, the draft and any uploaded photos are lost.

Note: the guidelines say permits must be submitted "3 working days in advance". The system does not enforce this. It accepts a permit starting today, so site discipline is up to supervisors.

Common pitfalls and edge cases (PTW)
  • Button does nothing: usually a remark or reason longer than 150 characters, or an expired session. Shorten the text, or sign in again.
  • Empty Manufacturing Number list: the project has no equipment of type "MFG NO", or the units were registered under another type. An administrator must fix this in Equipment List.
  • Empty Work Type list: no PTW templates are active. IT must add them.
  • Permit stuck at a stage: nobody holds the needed role, or, for approval, no main-contractor user is an approver.
  • Old permit appears when clicking "New": you reached the form some way other than the New menu item, for example with the browser Back button. Use the menu.
  • Two people act at once: the last save wins and can overwrite the other person's sign-off. Coordinate with each other, and reopen the list before acting.
  • Same person at several stages: the system does not stop one person who holds several roles from approving their own permit. This must be controlled by policy.
  • Permit not closed after the end date: it stays APPROVED until someone completes or revokes it.
  • Unused screen sections: "Equipments to be Used" and staff lists exist in the design but are switched off. Record the crew size in Total Worker.

Toolbox Meeting (TBM)

Daily

The electronic record of the short safety briefing a supervisor holds with the crew before each work session, morning (AM) or afternoon (PM). It proves the team was briefed on the day's work, hazards and safety checks. It also feeds the "Manpower at Site" figures on the dashboard.

Feature overview

One TBM record covers one session (AM or PM) on one day. It captures:

  • the briefing questions;
  • who attended;
  • the hazards discussed and the counter-measures;
  • which lift or escalator units are being worked on;
  • an equipment-specific safety checklist;
  • the team's goal for the day;
  • worker feedback;
  • photos;
  • four personal declarations by the person in charge.

An HEA Project Manager then approves it.

Key terminology
  • Session (AM / PM): decided by which Work Description you fill in. Exactly one of the two must be filled.
  • Attendee: a worker present at the briefing. Pick from users of your own company linked to the project.
  • Hazard / Issue Record: one hazard. It records the work activity, the cause, what could happen, and the action priority with remarks.
  • Action priority:
    • Priority 1: environment and facilities (elimination, substitution, engineering control)
    • Priority 2: people and behaviour (administrative control)
    • Priority 3: protective equipment (PPE)
  • Machine Type: Elevator or Escalator. It decides which safety checklist appears.
  • Today Team Action Goal: the team's safety goal for the session, e.g. "Zero open landing doors left unattended".
  • Touch and Call: the point-and-call safety phrase chanted by the team, e.g. "Harness hooked – Yoshi!".
  • Declarations: four mandatory tick boxes in which the person in charge accepts responsibility.

The "main contractor" rule explained

Each project names one main contractor, typically Hitachi Elevator Asia. A user counts as main contractor when the company on their profile is exactly that company. Main-contractor staff:

  • see every permit in the project, instead of only their own company's;
  • are the only ones who can give Part 4 approval;
  • see approved permits in Pending for daily review and revocation.

If an HEA manager "can't see" permits, check that their profile's Contractor Name matches the project's Main Constructor exactly.

FAQ and day-to-day troubleshooting

Daily operations checklist
  • Approvers (Assessor, Safety, Project Manager, CCP Approver): open your Pending lists at least twice a day. Nobody is notified automatically.
  • Supervisors: submit a toolbox meeting for every AM and PM session, with all attendees. This is the only source of manpower figures.
  • Applicants: complete the daily review on the day itself or the next day. Check your List for RETURNED items, and click Complete the Permit when the work ends.
  • Admins: when someone leaves, delete their account. When someone joins, create the account, add roles, and make sure their company is linked to the project.
"I can't log in."
  • Contractor staff: type your full email address. Without "@", the system adds "@hitachi.com".
  • The password is case-sensitive. Use the eye icon to check what you typed.
  • Was your account deleted? Deleted accounts cannot log in. Ask an admin to re-create it.
  • Forgot your password: an admin clicks Reset Password and you get a new one by email.
"I don't see my project."
  • Your company must be the main contractor, or be added under Project Configuration → "1. Contractors". Alternatively, you must be added personally under "2. Manpower & Staff".
  • The project may have been locked. IT must reactivate it.
"A menu item or button is missing."
  • Menu items depend on your roles. Ask an admin which roles you have.
  • The left menu only appears after you select a project.
  • Action buttons only appear at the right status and for the right role. For example, the Approve button for a toolbox meeting needs PTW APPROVER, and you cannot approve your own TBM or CCP.
"My Pending list is empty, but I know there are forms waiting."
  • Check you have selected the right project.
  • Toolbox meetings need PTW APPROVER, not TBM APPROVER.
  • PTW final approval: your profile's company must equal the project's main contractor exactly.
  • Reopen the Pending page from the menu. The list is a snapshot taken when the page was opened.
"I clicked Submit / Approve and nothing happened."
  • Scroll up and look for red validation messages.
  • Shorten long remarks or reasons to under 150 characters, and descriptions to their limits.
  • Your session may have expired, or the server restarted. Sign in again. Unsaved drafts are lost.
  • PTW: check the dates. The start cannot be in the past, and the permit can cover at most 7 days.
"The Manufacturing Number / Work Type / Key Activity list is empty."
  • Manufacturing Number: the project needs active equipment of type MFG NO.
  • Work Type, Key Activity and checklist questions are set up by IT. Ask IT to add them.
"Clicking New shows an old form."

Always open forms from the New menu item. Using the browser's Back button or a bookmark can reopen the last form you viewed.

"The PDF won't download."
  • TBM: a PDF attachment on the meeting probably breaks the export. Remove the PDF, or attach images instead.
  • PTW: a corrupt photo can stop the export without any message.
  • If all PDFs fail, the server's Crystal Reports component is missing. Contact IT.
"A closed permit stays in my Pending list forever."

This is a known defect. Once you have done the Closure Review, the Review button disappears and you can ignore the item.

"A permit was revoked by mistake."

There is no screen to undo this. IT has a database script that restores revoked permits to Approved. Ask IT, and provide the project, MFG No., dates and applicant.

"An uploaded document doesn't appear in Document List."

This is the long-project-name defect described in the Documents tab. Report it to IT.

"Error messages show technical details."

The site is configured to show full technical error pages. Take a screenshot and send it to IT. It helps them diagnose the problem.

Operational dependencies to keep running
  • Database server: SQL Server (2017 compatibility). The production database is "ePTW_PRD", about 45 GB including its log. Almost all of it is photos and documents, which are stored inside the database. Back it up accordingly.
  • Email: the system does not send email itself. It drops password emails into a queue in a separate database called "HEAData". Another program, which is not part of this system, sends them. If password emails stop arriving, check that program.
  • Web server components: the DevExpress 23.2 user-interface library, and the SAP Crystal Reports runtime for PDFs.
  • Sessions: held in the web server's memory. A server or app restart signs everyone out and loses unsaved drafts. Schedule maintenance out of hours.
  • Possible companion mobile app: the personal QR code, a GPS-logging table and a "currently valid permits" lookup suggest that a mobile app exists. It is not part of this code. Ask the team whether one is in use.
